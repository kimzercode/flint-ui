Tooltip

A short label that names an icon-only control — hover or keyboard focus, gone on leave. CSS only, zero JavaScript.

Usage

A tooltip names an element's function in label-length text. It is supplementary — the control must work, and make sense, without it. The M2 spec's own do-cases:

Use it forExample
Icon-only interactive imagery — controls with no visible textA printer icon → "Print ⌘ + P"
Distinguishing similar elementsThree align icons → "Align left / center / right"
Distinguishing icon-only actionsCut, copy, paste — same-ish glyphs, one word apart

Don't use it for

  • Restating visible text — a PRINT button already says PRINT; a tooltip repeating it is noise (an explicit M2 don't).
  • Rich content — avatars, cards, names and emails belong to a dialog or a popover, never a tooltip (also an explicit M2 don't).
  • Anything the user must not miss — tooltips vanish; important information lives in the page, a snackbar, or inline text.
  • Every control — tooltips describe differences; labeling the obvious interrupts the task.

Keep the text succinct (1–5 words) and in sentence case — "Align left", not "Aligns the current paragraph to the left margin of the document".

No shadow — twice agreed

M2's tooltip spec says 'don't display shadows on tooltips' in its own don't panel, so the flat rule needed no exception here. The grey-800 container (#3c4043, the Google-2020 idiom) does the separation, with white caption text.

Snackbar — the other dark surface

Anatomy

  1. Text label — 12px caption, sentence case, white, centered; wraps at 240px if it must.
  2. Container — grey 800, 4px radius, 24px tall, no arrow, no shadow. A plain rectangle, per the spec.
  3. Gap — 8px from the anchor (16px on touch-size screens, with a 32px-tall container — M2's mobile spec).
  4. Anchor — the control being named; it keeps its own aria-label (see accessibility).

Behavior

  • Zero JavaScript — the component is pure CSS: :hover and :focus-within do everything. Works with flint.js loaded or not.
  • Markup contract: a .fl-tip wrapper around the trigger, plus a .fl-tip__bubble with role="tooltip" and an id; the trigger points at it with aria-describedby.
  • Hover shows after 300ms (--fl-tip-delay) so sweeping a toolbar doesn't fire every tooltip; focus shows immediately.
  • Anchored to the target, not the cursor — it appears centered on the control and stays put while the pointer moves within it (the spec's behavior figure). It hides when the pointer leaves the target.
  • Stays while focused — keyboard focus keeps it visible until blur, per WCAG 1.4.13 (hover/focus content persists while the pointer or focus remains).
  • Four directions — fl-tip--bottom, fl-tip--left, fl-tip--right, top by default. There is no auto-flip (that needs JS positioning): near a viewport edge, pick the inward direction — that's how the spec's "keep the position visible / don't crop" rule is honored without script.
  • Touch: M2's mobile trigger is long-press, which CSS can't do — not shipped in 0.4. Tapping a button focuses it on Android, so :focus-within often shows the tooltip there; iOS Safari doesn't focus buttons on tap, so it won't. If you need the long-press pattern, it's a few lines of your own JS toggling a class.
  • Fade only — 150ms in and out, per the spec's transition pattern; prefers-reduced-motion makes it instant.
  • Never interactive — the bubble is pointer-events: none; it can't be hovered, clicked, or selected.

Accessibility

  • The bubble gets role="tooltip" and an id; the trigger points at it with aria-describedby — the ARIA Authoring Practices tooltip pattern.
  • The trigger must have its own accessible name — aria-label on an icon button, or visible text. The tooltip is never the sole carrier of a control's identity: it's visually helpful, the label is what assistive tech relies on.
  • Keyboard parity — :focus-within shows the same tooltip for Tab users, immediately (no 300ms wait).
  • Hidden state uses visibility: hidden + opacity, so an invisible bubble is out of the accessibility tree; visible state is announced as the control's description.
  • Known gap, honestly: WCAG 1.4.13 also asks that hover/focus content be dismissible with Escape without losing focus — CSS can't do that. Impact here is low because the tooltip only restates the control's own label and covers nothing; if your audit requires it, one keydown listener toggling a class closes it.
  • Touch gap, honestly: no long-press in 0.4 (see behavior). Don't gate a feature on the tooltip being reachable on touch.
  • Contrast: white on grey 800 (#3c4043) is ~10.6:1 — well past AA at 12px.

Code

<link rel="stylesheet" href="css/flint.css">

No script tag needed — this component is CSS only.

An icon button with a tooltip (the core pattern):

<span class="fl-tip">
  <button class="fl-icon-btn" aria-label="Align left" aria-describedby="tip-al">
    <svg viewBox="0 0 20 20" width="20" height="20" fill="currentColor" aria-hidden="true">…</svg>
  </button>
  <span class="fl-tip__bubble" id="tip-al" role="tooltip">Align left</span>
</span>

The four directions — one modifier on the wrapper, top by default:

<span class="fl-tip">…</span>                    <!-- above (default) -->
<span class="fl-tip fl-tip--bottom">…</span>     <!-- below -->
<span class="fl-tip fl-tip--left">…</span>       <!-- beside, pointing left -->
<span class="fl-tip fl-tip--right">…</span>      <!-- beside, pointing right -->

Theming

Everything is a CSS custom property on :root — override inline or in your own stylesheet, no rebuild:

TokenAffects
--fl-tooltip-bgThe container fill (grey 800)
--fl-surfaceThe label color on it
--fl-fs-captionThe 12px label size
--fl-radiusCorner radius (4px)
--fl-tip-delayThe hover show delay (300ms; focus never waits)
--fl-z-tooltipLayer order (above FABs, below topbar/snackbar)
--fl-dur / --fl-easeFade timing
 
:root {
  --fl-tooltip-bg: #0b8043;   /* a green tooltip, Google-2020 green 800 */
}
