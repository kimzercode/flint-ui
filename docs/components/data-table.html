Data table

Records in columns — flat 1px outline, 56/52px rows, selection, sorting and link-based pagination, zero JavaScript.

Usage

A data table compares many records across the same columns. Scanning one column downward is the task, so the structure is a real <table>: row headers, column headers and cells stay machine-readable for screen readers and for “copy to spreadsheet”.

Do use it when

  • The user compares values in a column — cost, date, status — and the comparison is the point.
  • There are more than three fields per record, or the header labels are what make the data legible.
  • The set has sorting, filtering or paging: the table is where those controls belong (M2 puts filters directly above the header row).
  • Rows are entities of one kind — deployments, invoices, members.

Don't use it when

  • The record is content, not a row: a note with a title, snippet and timestamp is a list row, and reading it matters more than comparing it.
  • Each record needs different fields — that is a card grid, not a table.
  • The table would need nested tables or merged cells to make sense; the data model is wrong, not the layout.
  • You only have two columns of short values — a list of label/value pairs reads faster.

The phone answer

The table scrolls horizontally (the selection column stays pinned) and the docs ship a recipe for the other phone pattern: render the same records as two-line list rows below 600px. One structure in the library, two presentations of the same records in your app — see the code.

Anatomy

Signal name Updated Cost
Offline Cosmo: prod shared vms 2 min $1,240
Online Astrid: NE shared managed-features 12 min $860
  1. Container — 1px outline, 4px radius, no shadow (0dp elevation). M2's spec is already flat here; Flint did not have to deviate.
  2. Header row — 56px, medium weight, secondary text. No fill and no vertical rules: weight separates the header (M2).
  3. Rows — 52px, 1px dividers in --fl-divider, 16px cell padding (16 + 16 = the spec's 32dp gutter).
  4. Selection column — reuses .fl-check. The cell is a 48px target, sticks to the left edge when the table scrolls, and carries a 1px divider (see the note below).
  5. Sort control — a 48px button (or link) in the header; the arrow is drawn from aria-sort on the <th>.
  6. Numbers — --num right-aligns and switches to tabular figures so digits line up.
  7. Toolbar — filter chips directly above the header row, inside the container (M2's placement).
  8. Footer — rows-per-page, range text, and four 48px pager controls.

One deliberate line

M2 draws no vertical rules. Flint adds a single 1px divider after the sticky selection column: with no shadow allowed, it is what stops a horizontally scrolled row from looking like text cut off mid-word. Without horizontal scrolling the line is a quiet gutter; with it, it is the only separation available.

Behavior

Sorting is author state

The library styles the sort control and reads the direction from aria-sort on the header cell — it never sorts anything. Server-rendered apps use a link:

<th scope="col" aria-sort="ascending">
  <a class="fl-data-table__sort" href="?sort=status&amp;dir=desc">
    <span class="fl-data-table__truncate">Status</span>
  </a>
</th>

Client-side apps use a button and flip the attribute. Either way the arrow's space is reserved (opacity only), so sorting never reflows the header. While a sort request is in flight, show progress with the existing linear progress bar above the table — no new component.

Selection reuses the checkbox

Row tint is :has(.fl-check:checked) — the same tint language as selection controls, lists and chips. Each selection cell wraps the input in a <label> so the whole 48px cell is the target, and the aria-label names the row.

Select-all is app state, not library state. The demo's script is ten lines; without it every row still toggles and tints, only “select all” is inert:

const table = document.querySelector(".fl-data-table");
const all = table.querySelector("thead .fl-check");
const rows = [...table.querySelectorAll("tbody .fl-check")];
all.addEventListener("change", () => rows.forEach((box) => { box.checked = all.checked; }));
rows.forEach((box) => box.addEventListener("change", () => {
  all.checked = rows.every((row) => row.checked);
}));

Pagination is links

First / previous / next / last are links with a query string, so they work with JS off and can be opened in a new tab. Unavailable directions render as a span with role="link" and aria-disabled="true" — greyed, not focusable, still announced.

The rows-per-page <select> is the one control that needs a submit path with JS off: wrap it in a <form method="get"> with a submit button, or let your app handle change. A select that changes the URL by itself is a script, and the library ships none.

Sticky column, not a second structure

Below roughly 900px of table width the table scrolls inside its container while the selection column stays put, so the checkbox never scrolls away. Nothing is duplicated: it is the same <table> with position: sticky on the first cell, and the sticky cell paints the row's own background so nothing shows through it.

Truncation is explicit

Auto table layout ignores max-width on cells, so a column does not shrink to fit — it widens and the table scrolls. When a value must truncate, wrap it in the slot and cap the slot:

<td>
  <span class="fl-data-table__truncate" style="max-width:180px;">
    Phoenix: prod shared lyra-managed-features
  </span>
</td>

For a truncated header, wrap the sort control in .fl-tip so the full label is available on hover and on keyboard focus — exactly what the demo's last column does.

Deliberately not shipped

  • Inline per-cell menus (the ⋮ inside a row) as a table feature — use a trailing .fl-icon-btn or a menu in a cell; the table does not own it.
  • Column resize, row drag, row grouping, aggregates — data-grid territory, and every one of them needs JavaScript.
  • A sticky header row — deferred until a real screen needs it; it interacts with the sticky column and the shell's scroll.
  • Sorting, filtering and paging logic — the library never touches your data.

Accessibility

  • It is a real table. A <caption> or aria-label names it, scope="col" ties headers to cells, and each row's checkbox is named ("Select Cosmo deployment"). Screen readers can read by row or by column.
  • Sorting is announced. aria-sort on the header is the state; the visible arrow is only its picture. Set aria-sort="ascending" / "descending" on the active column and leave it off everywhere else.
  • Targets are 48px. The sort control, the selection cell (the label, not the 18px box) and every pager control clear the M2 minimum; footer text and range are not interactive.
  • Unavailable pager directions are announced, not hidden. role="link" + aria-disabled="true" reads as a dimmed link; a plain greyed span would read as nothing.
  • The sticky column does not change the reading order. It is the first cell of the row in the DOM and stays the first cell visually; horizontal scrolling does not reorder anything.
  • Works without JS. Selection, tint, hover, sorting links and paging links are native/CSS. Two things need author code: select-all, and applying the rows-per-page select.
  • Hover is a bonus. The row hover layer is behind @media (hover: hover); the selected tint is not, so touch users still see what they picked.

Code

Two files bring the library in; the table is a table, plus four class names for the chrome and the controls.

<link rel="stylesheet" href="css/flint.css">
<script src="js/flint.js" defer></script>
<!-- Full table: sticky selection column, one sortable header, numeric column -->
<div class="fl-data-table">
  <div class="fl-data-table__scroll">
    <table aria-label="Recent deployments">
      <thead>
        <tr>
          <th scope="col" class="fl-data-table__check">
            <label>
              <input type="checkbox" class="fl-check" aria-label="Select all rows">
            </label>
          </th>
          <th scope="col" aria-sort="ascending">
            <button class="fl-data-table__sort" type="button">
              <span class="fl-data-table__truncate">Status</span>
            </button>
          </th>
          <th scope="col">Signal name</th>
          <th scope="col" class="fl-data-table__num">Cost</th>
        </tr>
      </thead>
      <tbody>
        <tr>
          <td class="fl-data-table__check">
            <label>
              <input type="checkbox" class="fl-check" aria-label="Select Cosmo deployment">
            </label>
          </td>
          <td>Offline</td>
          <td>Cosmo: prod shared vms</td>
          <td class="fl-data-table__num">$1,240</td>
        </tr>
      </tbody>
    </table>
  </div>
</div>
<!-- Footer: rows-per-page, range, pager. Links by default; unavailable
     directions are spans with role="link" aria-disabled="true". -->
<div class="fl-data-table__footer">
  <label class="fl-data-table__perpage">
    Rows per page
    <span class="fl-data-table__select">
      <select aria-label="Rows per page">
        <option selected>25</option>
      </select>
    </span>
  </label>
  <span class="fl-data-table__range">1–25 of 132</span>
  <nav class="fl-data-table__pager" aria-label="Table pagination">
    <span class="fl-data-table__page fl-data-table__page--first" role="link" aria-disabled="true" aria-label="First page"></span>
    <span class="fl-data-table__page" role="link" aria-disabled="true" aria-label="Previous page"></span>
    <a class="fl-data-table__page fl-data-table__page--next" href="?page=2" aria-label="Next page"></a>
    <a class="fl-data-table__page fl-data-table__page--last" href="?page=6" aria-label="Last page"></a>
  </nav>
</div>
/* Author CSS — the phone answer: same records, list rows below 600px. */
.records__list { display: none; }
@media (max-width: 600px) {
  .records__table { display: none; }
  .records__list { display: block; }
}

Render both from the same data and let CSS pick the presentation — the table's columns above, a two-line list row below. The selection column and the pager stay in the table; the list rows link to the same record.

Theming

Everything is a CSS custom property — override inline or in your own stylesheet, no rebuild. --_-prefixed properties are internal state tokens and not part of the API.

TokenAffects
--fl-table-head-hHeader row height (default 56px)
--fl-table-row-hBody row height (default 52px)
--fl-borderContainer outline, select border
--fl-dividerRow dividers, sticky-column divider
--fl-hoverRow hover, pager hover
--fl-tintSelected row fill
--fl-text-secondaryHeader text, inactive pager
--fl-disabledUnavailable pager directions
--fl-accentFocus rings (sort, pager, select)
 
:root {
  --fl-table-row-h: 44px;   /* dense tables on a data-heavy screen */
  --fl-tint: #e6f4ea;       /* selected rows tint green */
}

Dense rows are a token, not a second component: 44px still fits a 14px label with 16px padding. A table with a selection column keeps a 48px floor on the checkbox cell, so dense rows are for read-only tables — a shorter checkbox target is not a trade this library makes. That is also why the default is 52px.
