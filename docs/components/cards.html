Cards

Outlined content containers, no shadows — flat surfaces for related content and actions.

Usage

Cards group related content and its actions on a single bordered surface. In the M2 2020 style they are quiet: a 1px border does the separation work that a shadow would do elsewhere, so cards read as *containers*, not as floating layers.

Do use it when

  • Content pieces are heterogeneous — a title, a paragraph, actions, maybe a nested detail — that belong together.
  • You need scrollable feed content (the mail-style timeline in the demos: section label, then a stack of cards).
  • The card hosts a self-contained interaction (a notification with Dismiss/Upgrade actions).

Don't use it when

  • Items are peers of the same structure — that is a list, not a card stack; rows are lighter and denser.
  • You need a modal surface — the dialog (planned 0.4) over the scrim is that, not a positioned card.
  • Everything on the page would be a card — borders everywhere is visual noise; let section labels and spacing carry quiet groupings.

Card vs. list row

Cards for varied, self-contained content. Lists for repeated, peer items. The demos mix them: card stacks in the feed, list rows in the inbox.

Lists

Anatomy

  1. Surface — white, 1px --fl-border, 8px radius (--fl-radius-card), 16px padding. Never a shadow.
  2. Title — 16px/500 (--fl-fs-title), the card's h2–h4 level.
  3. Text — 14px body in secondary color.
  4. Action row (optional) — text button left of the filled one, right-aligned; mirrors the auth-card convention.

Behavior

  • Stacking: adjacent cards get a 16px gap automatically (.fl-card + .fl-card) — wrap a feed in a container and the rhythm is free.
  • Grouping: fl-section-label (uppercase caption) heads each group; it collapses its top margin as the first child of a container.
  • Cards are not interactive surfaces by default — no hover fill, no cursor change. Interactivity belongs to the controls inside. Whole-clickable cards are not in the library (planned pattern: make an inner link cover the card).
  • Composition: cards nest (the demos show a button row inside a card) and work with every shell's fl-content column, capped at --fl-content-max on desktop.
  • Width: block-level, fills its container — constrain the parent, don't set card widths.

Accessibility

  • Use a real heading element for fl-card__title and keep the page's heading order sane (cards are usually h2/h3, never skip levels for styling).
  • <article class="fl-card"> gives each card its own landmark-ish region in feed contexts (screen readers list the articles).
  • Action rows keep real buttons — same rules as the buttons page; right-aligned text-then-filled order preserves a logical focus order.
  • The border/separation is presentation, not semantics — no role needed on the card itself.

Code

Two files bring the library in; the markup below is the core pattern.

<link rel="stylesheet" href="css/flint.css">
<script src="js/flint.js" defer></script>
<!-- A labeled group of stacked cards (the feed pattern) -->
<main class="fl-content">
  <p class="fl-section-label">Today</p>

  <article class="fl-card">
    <h2 class="fl-card__title">Design review moved to 15:00</h2>
    <p class="fl-card__text">The flat-shell discussion is now after lunch.</p>
  </article>

  <article class="fl-card">
    <h2 class="fl-card__title">Quota update</h2>
    <p class="fl-card__text">Storage is at 68% of plan.</p>
    <div style="margin-top:16px; display:flex; gap:8px; justify-content:flex-end;">
      <button class="fl-btn fl-btn--text">Dismiss</button>
      <button class="fl-btn fl-btn--filled">Upgrade</button>
    </div>
  </article>
</main>

Theming

Everything is a CSS custom property on :root — override inline or in your own stylesheet, no rebuild:

TokenAffects
--fl-borderThe card's 1px separation
--fl-radius-cardCorner radius (8px)
--fl-fs-title / --fl-fs-bodyTitle / text sizes
--fl-text-secondaryBody text color
--fl-space-3Card padding and stack gap
 
:root {
  --fl-radius-card: 12px;   /* soften the corners */
}
