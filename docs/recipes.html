Recipes

Flint recipes are compositions: existing components plus a few lines of author CSS for layout only. Nothing here adds classes to the library — that keeps the component contract small and the recipes copy-pasteable.

Card grid

The Keep-style wall of note cards: a CSS grid of fl-cards that reflows from one column to as many as fit, no media queries — auto-fill does the work. Two lines of author CSS:

<style>
  .fl-card-grid {
    display: grid;
    grid-template-columns: repeat(auto-fill, minmax(240px, 1fr));
    gap: var(--fl-space-2);              /* Keep's tight 8px rhythm */
  }
  .fl-card-grid .fl-card { margin-top: 0; }  /* kill the stacked-card margin */
</style>

Cards that navigate or open an editor are real interactive elements — a <a class="fl-card"> or <button class="fl-card">, never a div with a click handler:

<div class="fl-card-grid">
  <button class="fl-card" type="button">
    <h2 class="fl-card__title">Packing list</h2>
    <p class="fl-card__text">Smores, extra towel, warm socks…</p>
  </button>
  <a class="fl-card" href="/note/42">
    <h2 class="fl-card__title">Q3 roadmap</h2>
    <p class="fl-card__text">Ship the rail shell, then the menu.</p>
  </a>
</div>
  • No-JS: the grid is pure CSS; every card works as its native element (anchor navigates, button clicks).
  • 240px floor: three cards fill a 960px reading column; phones get one column without a media query. Raise the floor for wider cards, never below ~200px.
  • Selection tint: for selectable cards combine with the checkbox lesson from the Lists page: .fl-card:has(.fl-check:checked) → tint. The checkbox owns the state, the card reads it.
  • Masonry is a gap, deliberately: variable-height card walls need grid-template-rows: masonry, which no engine ships. Equal-height rows are the honest web version.

Empty state

M2 has no empty-state spec; Google's apps draw it as a centered stack — large muted icon, one title line, one supporting line, and (optionally) one action. Composed from existing pieces, the author CSS is only the stack:

<style>
  .fl-empty {
    display: grid;
    justify-items: center;
    gap: var(--fl-space-2);
    padding: var(--fl-space-4);
    text-align: center;
    color: var(--fl-text-secondary);
  }
  .fl-empty .fl-icon { width: 48px; height: 48px; border-radius: var(--fl-radius-card); }
  .fl-empty__title { margin: 0; font-size: var(--fl-fs-title); font-weight: 500; color: var(--fl-text); }
</style>
<div class="fl-empty">
  <span class="fl-icon" aria-hidden="true"></span>
  <h2 class="fl-empty__title">No notes yet</h2>
  <p>Notes you add appear here.</p>
  <button class="fl-btn fl-btn--outline" type="button">Take a note</button>
</div>
  • Announce it once: the empty state is normal content — no aria-live, no role="status". It renders where the list would render.
  • One action maximum — the empty state is a signpost, not a toolbar. More than one action means the screen isn't actually empty.
  • Swap the placeholder for a real 48px icon when you have a set — the recipe doesn't change.

Keep-style app shell

The form factor Google Keep web uses, assembled from the 0.5 components — this is the same composition the samples/ notes app is built on. Nothing here is new CSS beyond the two recipes above:

RegionMobile (<905px)Desktop (≥905px)Component
Navigation Bottom tab bar Permanent 80px icon rail Rail shell — one markup, CSS flips it
Top bar Transparent, search pill as the anchor Top app bar — --transparent + __search
Content Card grid (recipe above) fl-card + .fl-card-grid
Create Flat FAB FAB
Note editor Centered dialog (Keep web's editing surface) Dialog — --fullscreen for full-screen mobile flows
Delete confirm Centered dialog Dialog
Per-note menu ⋮ dropdown on the card Menu
Status / undo Inverse-surface snackbar Snackbar
Filters Modal side sheet Standard side sheet (or dialog) Side sheet

A runnable skeleton of the whole table lives at demos/recipe-keep.html — open it at both widths and watch the shell flip. The app logic (notes data, undo, discard-blank) is author code by contract; the recipe supplies every piece of chrome.

Why no master-detail split

M2 has no spec for a two-pane layout and Google's own web apps disagree (Gmail = split, Keep/Drive = overlay). Flint's wide-screen answer is the side sheet, composed above; a master-detail guide may follow once a real Gmail-web reference audit can back it.
